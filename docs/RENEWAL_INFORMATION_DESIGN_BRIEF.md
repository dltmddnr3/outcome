### Comprehension test protocol (not yet executed)

Use the same factual fixtures for baseline and redesign. Ask the participant to explain in their own words, without teaching the terms first. | Scenario | Question to participant | Critical wrong inference to prevent |
| --- | --- | --- |
| Boundary ready, result not yet produced | What can you use now, and what happens next? | “The deliverable is complete” |
| Confirmed result awaiting acceptance | What is ready, and what does the confirmation decide? | “Opening the result publishes it” |
| Current and historical counts differ | Which number describes the current scope, and is completion established? | “The historical larger count means current completion” |
| Source conflict | What cannot be trusted yet, and what is needed to resolve it? | “Everything is broken” or “all complete” |
| No observed runtime state | Can you tell whether the agent is working? | “No observation proves stopped” |
| Message accepted, delivery unknown | Has the Planner received it? Is another send safe? | “Accepted means delivered” or blind resend |
| Approval absent, evidence incomplete | Do you need to decide anything now? Is the project finished? | “No approval card means all work complete” |
| Document-based purpose discovery | What has been saved, what is undecided, and has a project been created? | “Uploaded document means verified plan/project creation” |
| Mobile tab switch with a draft | Where is the draft and pending decision after switching? | Lost context or duplicate submission |
| Expired authentication | What can you do to return, and is private project data shown? | Private state leakage or false successful logout |

Acceptance proposal: no critical wrong inference in the observed final scenarios; all required facts/actions reachable by keyboard and screen reader. Report actual participant/session counts, not fabricated usability percentages. A single owner's dogfood can demonstrate that owner's comprehension, not general-population usability.
